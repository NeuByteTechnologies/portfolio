# DATA DICTIONARY — MODULE 6: LOGGING & EVENTS
This module defines the entities used to track application‑level events, categorize those events, and record system errors. These tables support observability, diagnostics, analytics, and operational insight.

Your logging subsystem is intentionally lightweight and appropriate for a consumer fitness application.

## Table: event_type
**Description:**
Defines the categories of events that can occur within the application.
Used by app_event to classify user actions, system actions, and domain events.

|Column | Type | Null | Description |
|-------|------|------|-------------|
|event_type_id | TINYINT | NO | Primary key.|
|event_type_name | VARCHAR(50) | NO | Name of the event type (e.g., “Workout Logged”).|
|event_type_description | VARCHAR(255) | YES | Optional description of the event type.|

**Business Rules:**
- Event types are system‑defined.
- Event types should be stable and rarely modified.
- Used for analytics, reporting, and notification triggers.

## Table: app_event
**Description:**
Stores application‑level events generated by user actions or system processes.
This table provides behavioral analytics and supports notification triggers.

|Column | Type | Null | Description|
|------|-----|-------|-------------|
|app_event_id | INT (IDENTITY) | NO	Primary key.|
|event_type_id | TINYINT | NO |FK → event_type.|
|user_id | INT | YES | FK → user. Null for system‑generated events.|
|event_timestamp | DATETIME2 | NO |	When the event occurred.|
|event_metadata | VARCHAR(MAX) | YES | Optional JSON or text metadata (e.g., workout_id, program_id).|

**Foreign Keys:**
 - event_type_id → event_type.event_type_id
 - user_id → user.user_id

**Business Rules:**
- user_id may be NULL for system events (e.g., scheduled jobs).
 - event_metadata may store contextual details (IDs, values, flags).
 - Used for analytics, insights, and notification_event triggers.

## Table: error_log
**Description:**
Captures application errors, exceptions, and failures for debugging and operational monitoring.

|Column | Type | Null | Description|
|-------|------|------|------------|
|error_log_id | INT (IDENTITY) | NO | Primary key.|
|error_timestamp | DATETIME2 | NO | When the error occurred.|
|error_message | VARCHAR(4000) | NO | Error message or exception summary.|
|stack_trace | VARCHAR(MAX) | YES | Full stack trace or diagnostic details.|
|user_id | INT |YES | FK → user. Null if error not user‑initiated.|
|context | VARCHAR(255) | YES | Optional context (API endpoint, module, operation).|

**Foreign Keys:**
 - user_id → user.user_id
-
**Business Rules:**
 - Errors should be logged for all unexpected failures.
 - user_id is optional because many errors occur outside user actions.
 - context helps categorize errors for debugging and reporting.
